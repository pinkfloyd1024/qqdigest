# qqdigest — QQ 消息定时整合系统

自动读取**大号** QQ 收到的消息 → 本地暂存 → 每天 12:00 / 18:00 / 22:00 交给**本地 Qwen3-14B** 整合 → 通过 QQ 发到**小号**。

**全程不调用任何在线大模型 API，消息内容不出本机。**

- 版本：1.0.0
- 依赖：**无**。纯 Python 标准库实现（含 tkinter 图形界面），要求 Python ≥ 3.11
- 实测环境：Windows + Python 3.11.9 + LM Studio(Vulkan, RDNA4) + RX 9070 XT 16GB

## 1. 图形界面（推荐）

双击项目根目录的 **`启动界面.bat`**，或者：

```powershell
python gui.py
```

界面共 8 个标签页：

| 页面 | 能做什么 |
|---|---|
| **运行状态** | 一键启动/停止后端、体检、**实时监听**、自检、生成简报、**立即整合并发送到 QQ**；查看今日档位、消息统计、后端实时输出 |
| **日志简报** | 浏览历史简报留档、查看运行日志 |
| **常规** | 发送时刻（可增删）、提前预计算分钟、各类窗口与容错参数、干跑开关 |
| **采集过滤** | 是否采集私聊/群聊、**群白名单**、会话黑名单、是否只整合收到的消息 |
| **重要通知** | **重要关键词**、**重要联系人/群**、标记前缀、命中后是否立即弹窗提醒；带「立即测试提醒」按钮 |
| **群标签** | 每个群打固定标签（课程/工作/学校/家人/技术/同学/聊天群/营销）并赋权重；一键自动识别；双击手工改；权重 0 的群不纳入整合 |
| **提示词** | 直接编辑系统提示词与摘要提示词、追加个人规则、**预览最终生效提示词**、一键载入/清空内置默认 |
| **QQ 接入** | 大号/小号 QQ 号、上报地址与鉴权、NapCat API 地址、分段参数；带「测试连接」 |
| **大模型** | 服务地址、模型标识、max_tokens、温度、上下文预算；带「测试连接」和「跑一次小样整合」 |

### 界面使用要点

- **改完必须点「保存配置」**。保存时会：① 校验取值合法性；② 写回 `config.toml`（**保留全部注释**）；③ 自动备份到 `config.toml.bak`；④ 二次解析校验，失败自动回滚。
- **后端是独立进程**。界面只负责编辑配置和显示结果，采集/调度在 `python run.py run` 子进程里跑。所以关掉界面不影响消息采集；反过来，改了配置需要**重启后端**才生效（界面会提示）。
- 点「启动后端」时会先静默保存一次配置，避免界面上的改动没落盘。
- 关闭界面时会问你是「停止后端并退出」还是「保持后端运行，只关界面」。

> 想让界面无控制台窗口运行就用 `启动界面.bat`（内部用 `pythonw`）。
> 若启动失败，错误详情会写入 `logs\gui-error.log` 并弹出系统提示框。

## 2. 它是怎么工作的

```
大号 QQ ── NapCat(OneBot 11) ──HTTP 上报──▶ run.py 上报服务端
                                                  │
                                                  ▼
                                        data/store.db（本地 SQLite 暂存）
                                                  │
                        每天 12:00/18:00/22:00 提前 5 分钟
                                                  ▼
                       POST http://127.0.0.1:1234/v1/chat/completions
                              （本地 Qwen3-14B，加 /no_think）
                                        │
                          代码拼接「【重要提醒】」小节
                                        │
                                 结果写入 runs/*.md 留档
                                        │
                          到点 ──▶ NapCat HTTP API ──▶ send_private_msg ──▶ 小号
```

### 关键设计 1：两段式「提前预计算 + 整点发送」

```
11:55  采集窗口截止 → 交给本地模型整合 → 结果暂存到数据库
12:00  从数据库取出 → 发给小号
```

**采集窗口的结束边界 = 预计算时刻**，不是发送时刻：

```
窗口 = [上次预计算时刻, 本次预计算时刻]
下一次窗口从 11:55 开始（而不是从 12:00 开始）
```

这样 11:55~12:00 之间到达的消息**不会被丢掉**，它们顺延进下一档（18:00 那批），总体零丢失。
好处：整点必定准时送达、多出 5 分钟重试窗口、与 GPU 占用解耦、结果提前落盘可人工干预。

### 关键设计 2：重要提醒由代码生成，不交给模型

命中「重要关键词 / 重要联系人」的消息会被打上标记（默认 ⭐），程序在简报最前面**用自己的代码**拼出「【重要提醒】」小节，逐条列出是谁、什么时候、说了什么。

**踩坑记录**：最初的实现是把「请输出【重要提醒】小节」写进系统提示词交给模型做。实测发现，14B 模型在同时承担「抽取重要项」和「四分类」两件事时开始丢内容——出现过整条消息被漏掉的情况（张伟的评审通知凭空消失）。改成代码拼装后，重要项零遗漏，四分类也恢复到一条不漏。**约束一多就掉质量，这是小模型的固有特性。**

### 关键设计 3：会话标签与权重（解决"信号稀释"）

给每个会话打一个**固定标签**（课程/工作/学校/家人/技术/同学/聊天群/营销），每个标签带一个权重。
整合时**按权重从高到低依次处理**——先工作/课程，最后聊天群，**权重 0 的群（营销、垃圾群）直接不进入上下文**，只在简报末尾报一行条数。

三级判定，逐级回退：

| 优先级 | 方式 | 说明 |
|---|---|---|
| 1 | `manual` 手工指定 | 你比模型清楚哪个群是什么，永远优先；界面上双击一行就能改 |
| 2 | `keywords` 关键词 | 命中群名就直接定标签，**不消耗模型调用**；实测你的 15 个群里 4 个靠它命中 |
| 3 | 本地模型 | 把「群名 + 采样若干条消息」交给模型判断 |

**为什么要带采样消息**：仅凭群名对"小海豹群""某闲聊群"这类名字是无解的。实测带上几条消息后，
"小海豹群"被正确识别为技术群（群里在聊 AI 收集器和卡片），而"某数码促销群"被识别为营销群（权重 0，直接排除）。

**边界（必须说清）**：权重排序只能改变**先后**，改变不了**预算分配**。如果营销群有 500 条而课程群只有 2 条，
光靠排序帮助有限——**真正有效的是把权重设成 0 把它整个排除**。所以权重的正确用法是：
把没价值的群设 0，把重要的群设高，中间那些保持默认。

另一个限制：**群名分类不可能 100% 准**。所以做成了三级回退 + 手工覆盖，而不是全交给模型。

### 关键设计 4：群/私聊用视图分离，而不是拆成两张物理表

需求原本是"群消息和私聊分开存两张表"。实现时改成了 **SQL 视图 + 复合索引**：

| 视图 | 字段 |
|---|---|
| `v_group_messages` | 时间、群号、群名、发送者 QQ、网名、内容 |
| `v_private_messages` | 时间、对方 QQ、网名、方向、内容 |

两个视图都**自动排除静音（权重 0）的消息**。

**为什么不真的拆表**：`chat_type` 已经在表里且有索引；拆表会让每一次窗口查询都要 `UNION`、
去重逻辑写两遍、统计要跨表聚合，而收益只是"看起来分开了"。视图让查询和报表用起来就是两张独立的表，
底层数据不碎片化。如果将来确实需要物理隔离（例如群消息单独归档），再迁移也不迟。

### 关键设计 5：权重 0 是"标记静音"而不是"不入库"

需求原本是"权重 0 的私聊和群干脆不存储"。实现时改成了**照常入库 + 打 `muted` 标记**：

- 查询、视图、整合全部跳过它；
- 统计页可以单独勾选"包含静音消息"查看；
- `muted_keep_days`（默认 7 天）到期后由 `purge_muted` 清理，磁盘占用同样可控。

**为什么不直接丢**：标签是模型判断的、**会错判**。实测中 692 条消息的游戏群被模型判成了"技术群"，
一个真正的营销群也可能偶尔被判成聊天群。如果入库时就丢掉，事后把标签改回来也找不回历史消息。
标记是可逆的，丢弃不是。**存储很便宜（你 1822 条消息只占 0.4 MB），误删很贵。**

### 关键设计 6：把"我"和"别人"钉死

**这是一个真实 bug**：别人说"我明天请假"，简报里被写成"我需要明天请假"。

根因是四个分类标题（需要我回复 / 待办 / 值得知道）**天生是第一人称视角**，
模型会把别人的意图改写成我的。两道防线：

1. **渲染层**：我发的消息一律标注 `我(本人)`，别人的用昵称（群聊里还带 QQ 号），视觉上不可能混淆；
2. **提示词层**：明确写"别人说他要做什么，写成『某某说他要去做什么』，绝不能改写成我要做"，
   并给了正反例（"我明天请假" → 值得知道；"你明天把表给我" → 待办）。

### 关键设计 7：低权重会话的逐群预压缩

**解决什么**：一个 4 小时的窗口里，游戏群可能有 2000 条消息，而真正重要的私聊只有 3 条。
全塞给模型既慢又容易被闲聊稀释。

| 会话权重 | 处理方式 |
|---|---|
| `>= general.no_compress_weight`（默认 8） | **不压缩**，原文进上下文——重要内容不能被摘要损失 |
| `1 ~ 7` | **逐群压缩**成一个要点块，存进 `compressed_blocks` |
| `0` | 静音，根本不进上下文 |

**什么时候跑**：不另起定时器，而是在每次**预计算之前**跑一次。每小时一档的调度下，
这天然就是"工作时间内每小时压缩一次"，而且摘要刚生成就被用掉，不存在过期问题。

**一个容易写错的语义**：取摘要时的条件是"**块覆盖整个查询窗口**"
（`block_start <= start AND block_end >= end`），不是"块落在窗口内"。
用只覆盖一部分窗口的摘要会**替掉**块外的消息，导致内容凭空缺一截。
这个错误被测试抓了出来（`test_partial_window_summary_not_used`）。

实测效果：833 条消息 → 压缩 14 个低权重会话（775 条）→ 整合输入降到约 3600 tokens。

### 关键设计 8：QQ 消息排版由代码完成

**不让模型直接输出漂亮格式**：实测给 14B 模型加格式约束会连带掉内容质量
（出现过整条消息消失）。所以让模型只管"分四类、写清楚"，排版这件确定性的事交给代码。

发送到 QQ 的样子：

```
📮 消息简报　10-12 12:00 → 13:00
236 条　25 个会话　⭐ 2 条重要

┈┈┈┈┈┈┈┈┈┈┈┈
🔴 需要我回复　3 条
┈┈┈┈┈┈┈┈┈┈┈┈
1. 陈总：要求周五之前把季度预算表发到邮箱
2. wiki：让我办一件事（内容未说明）
```

- 四类用彩色 emoji 做图标（QQ 能渲染彩色 emoji），一眼分得清；
- 条目自动编号，模型不写 `- ` 前缀也能正确解析；
- 「可以忽略」常有几十条，**压成两行**免得刷屏；
- 头部的时段标签：定时发送是「上次成功发送 → 本次发送」，手动发送是实际数据范围；
- **留档 `.md` 里存的仍是模型原始输出**，排版只影响发到 QQ 的那一份。

### 关键设计 9：界面滚轮"就近滚动"

用户报的问题：鼠标停在白名单列表框上滚动时，整个页面跟着滚、列表不动。

根因是滚轮被无条件绑到页面级，并且用 canvas 的 `<Enter>`/`<Leave>` 开关绑定——
而表单控件是 canvas 的**独立子控件**，指针一移进子控件就触发了 `<Leave>` 解绑。

现在改成**常驻绑定 + 按指针位置路由**：落在列表框/文本框/树上是它们自己滚，
落在本页其它任何位置是页面滚，落在本页之外则完全不动。

### 关键设计 10：幂等

`digests.slot` 字段有 UNIQUE 约束（如 `2026-02-05T12:00`），保证同一档位**只会生成一次简报、只会发送一次**。进程崩溃重启、重复运行、界面和后端同时操作，都不会重复发消息。

## 4. 首次部署步骤

### 步骤 0：确认本地模型就绪

LM Studio 里加载 `qwen3-14b`，打开本地服务器（默认 `127.0.0.1:1234`）。

**并行槽建议设为 1**（命令行方式）：

```powershell
& "$env:USERPROFILE\.lmstudio\bin\lms.exe" unload --all
& "$env:USERPROFILE\.lmstudio\bin\lms.exe" load qwen/qwen3-14b --parallel 1 -c 16384 -y
& "$env:USERPROFILE\.lmstudio\bin\lms.exe" ps      # 确认 PARALLEL = 1
```

理由：9 GB 模型 + 多路 KV cache 会逼近 16 GB 显存上限，1 路更稳。

### 步骤 1：启动 NapCat 并登录大号

**NapCat 已经装好并预配置完毕**，位置：

```
<NapCat 安装目录>\NapCat.<版本>.Shell\
```

它**自带一个匹配版本的 QQ**，装在 `versions\<QQ版本>\` 里，**不会碰你现有的 QQ**——两边可以共存。

你只需要：

1. 双击 **`<NapCat 安装目录>\napcat.bat`**
2. 用**手机 QQ** 扫描控制台里出现的二维码，登录大号 `10000001`
3. 保持这个窗口开着（关了 NapCat 就停了）

> **两个接口已经预写好了**，不需要进 WebUI 手动配。配置文件在
> `<NapCat 安装目录>\versions\<QQ版本>\resources\app\napcat\config\`
> 下的 `onebot11.json` 与 `onebot11_10000001.json`：HTTP 服务端（`127.0.0.1:3000`）+ HTTP 上报（`http://127.0.0.1:5700/`，含「上报自身消息」）。
> WebUI 已改绑到 `127.0.0.1:6099`（默认是 `::`，局域网可达，不安全）。token 在同目录的 `webui.json` 里。

> ⚠️ NapCat 以**无界面**方式在后台运行 QQ。登录后电脑上就没有大号的聊天窗口了，日常收发大号消息用手机即可。手机上保持登录完全正常，且 NapCat 同样能收到你手机发出的消息。

> 📌 **为什么不能用你现有的 QQ？**
> 实测过：NapCat 的某个具体 build 只适配**特定版本**的 QQ。版本不匹配时，NapCat 注入 QQ 的过程会成功
> （能打印 `[NapCat Backend] Process resumed`），但它的 JS 层永远加载不起来——
> 表现为**没有任何日志、没有任何端口监听、QQ 也卡死在启动阶段**。官方排错文档也把"检查 NTQQ 版本兼容性"列为登录问题的第一条。
> 因此建议用官方一键包，让它自带一个完全匹配的 QQ，两个 QQ 互不干扰。
>
> 排查方法：在 `NapCatInstaller.exe` 里搜 `versions` 或看它下载的目录名，那个版本号就是它要求的 QQ 版本。

> 🧹 如果之前试过别的 NapCat 目录，确认不再需要后可以整个删掉。

### 步骤 2：验证上报链路（关键一步，别跳过）

这是整个搭建里最容易出问题的地方。开一个命令行窗口：

```powershell
cd <本项目的目录>
python run.py watch
```

然后在**手机上给自己发一条 QQ 消息**。命令行里应该立刻出现：

```
[17:06:20] 已收录   [private] 张三: 你好
```

看到这一行就说明**采集链路完全打通**了。看不到的话，程序退出时会列出 4 条排查清单。

界面里也有这个功能：「运行状态」页 → **「实时监听」** 按钮（会另开一个窗口）。

### 步骤 3：用界面完成配置

双击 `启动界面.bat`，然后：

1. **「QQ 接入」页** → 确认大号 `10000001`、小号 `10000002` → 点「测试连接」（应显示 NapCat 当前登录的账号）
2. **「大模型」页** → 点「测试连接」，应看到 `qwen/qwen3-14b` → 可再点「跑一次小样整合」看效果
3. **「采集过滤」页** → 决定是否采集群消息（建议只加白名单）
4. **「重要通知」页** → 填关键词和重要联系人 → 点「立即测试提醒」验证弹窗
5. 点 **「保存配置」**

### 步骤 4：启动并观察

在「运行状态」页点 **「启动后端」**。保持**干跑模式开启**（「常规」页），先跑一到两周：

- 后端会实时采集消息并入库；
- 每天提前 5 分钟自动生成简报；
- 到点**不发送**，只写留档、复制到剪贴板、打印日志。

随时在「日志简报」页检查简报质量，或用「生成简报」按钮立即试一份。

### 步骤 5：转为正式发送

质量满意后，在「常规」页**关闭干跑模式** → 保存配置 → 重启后端。此后每天 3 条简班会自动发到小号。

## 7. 常见问题

### 启动相关

**Q：双击 `启动界面.bat` 没反应，黑窗一闪就没了？**

启动器现在会先做一次自检再拉起界面。如果失败，它会**把原因直接打印在窗口里并停住等你按键**，同时完整堆栈写入 `logs\gui-error.log`。所以正常情况下不会再出现"什么都没发生"。

也可以手动自检：

```powershell
python gui.py --preflight
```

它会逐项检查 Python 版本、tkinter、项目模块、配置文件、目录可写性。

> ⚠️ **修改这个 .bat 时必须保持纯 ASCII，并且绝对不要在里面写 `chcp`。**
> 原因：cmd.exe 是按字节偏移重新读取批处理文件的。文件里一旦出现非 ASCII 字节（中文注释也算），再配合代码页切换，它就会读取错位、把后面的行撕碎执行，最终落进错误分支并**卡在隐藏的 `pause` 上**——表现就是"双击没反应"。
> 本机实测：GBK 编码的中文注释、UTF-8 编码的中文注释**都会**让它失效，纯 ASCII 正常。这个坑已用单元测试锁住（`tests/test_launcher.py`）。所有面向用户的中文提示都放在 `gui.py` 里。

**Q：界面能打开，但某个按钮点下去报错？**
把「运行状态」页下方「后端输出」的内容发出来，或查看 `logs\qqdigest.log`。涉及子进程的操作（启动后端、体检、自检）输出都会实时打印在那里。

**Q：启动时报「5700 上已经有服务在响应」？**
说明已经有一个 qqdigest 实例在跑（后端，或某次 `watch` 没关干净）。

这条检查是**故意加的**：Windows 的 `SO_REUSEADDR` 允许两个进程绑定同一端口，如果不拦，新实例会「启动成功」但**一条上报都收不到**——所有连接都被旧实例接走。你会对着一个僵尸进程调试，看到的是旧代码的行为，极难排查（这个坑真实发生过）。

处理：把旧实例关掉。命令行确认：

```powershell
Get-NetTCPConnection -LocalPort 5700 -State Listen | Select-Object OwningProcess
# 拿到 PID 后
Stop-Process -Id <PID> -Force
```

> 注意：Ctrl+C 或关掉终端窗口时，子进程未必一起退出。用上面的 PID 方式确认最可靠。

### 使用相关

**Q：模型返回的正文是空的？**
`llm.max_tokens` 被思维链吃光了。设为 3000 以上，或保持 `no_think = true`。程序检测到空正文会明确报错并提示，不会静默发空消息。

**Q：`chat_template_kwargs: {"enable_thinking": false}` 为什么没用？**
本机 LM Studio 实测该参数**不生效**（reasoning token 仍存在）。程序采用 `/no_think` 软开关，实测 reasoning 归零。

**Q：日志里出现"已错过且超出补发窗口，跳过"？**
正常。程序启动时会对已经过去太久（超过 `catch_up_max_min`）的档位登记跳过，避免开机瞬间补发一堆过期简报。这是幂等设计的一部分。「今日档位」表里会显示成「失败/跳过」。

**Q：重要消息和下面的分类重复了？**
是的，会重复。这是有意的：「【重要提醒】」是置顶的必看摘要，下面四个分类提供完整上下文。重要项由代码生成，不会漏也不会编造。

**Q：界面上改了配置，为什么没生效？**
需要重启后端。界面改的是 `config.toml`，后端进程在启动时读取一次。保存配置后界面会提示你重启。

**Q：界面保存配置会不会把 `config.toml` 里的注释弄丢？**
不会。写回器只定位并替换目标键值所在的字节区间，其余内容（包括所有注释和排版）原样保留；写盘前还会用 `tomllib` 重新解析一遍，解析不通过就拒绝写入。

**Q：界面会不会和后端抢数据库？**
不会。界面用**只读模式**打开数据库（`Store.open_readonly`），不写任何 PRAGMA、不建表、不迁移，因此不会和后端进程产生写冲突，也不会误创建空库。

**Q：简报太长被拆成多条？**
按 `target.max_chars_per_message`（默认 1500 字）自动分段，并在开头标注 `（1/3）`。

**Q：想整合群消息？**
在「采集过滤」页勾选「采集群聊」，并把要看的群号加入白名单。群消息量与私聊不在一个量级，建议只加真正重要的群。

**Q：桌面弹窗不出现？**
先在「重要通知」页点「立即测试提醒」看结果。若提示所有渠道失败，检查 Windows 设置 → 系统 → 通知，确认允许 PowerShell 发送通知。即使弹窗不可用，提醒仍会写入 `data/notices.log` 并复制到剪贴板。

**Q：怎么清空数据重来？**
停掉后端，删除 `data/store.db`（会丢失窗口水位线和历史简报记录）。

## 10. 已知限制

### 规模边界（实测数据）

单次整合的消息量决定了走「单次调用」还是「分块 map-reduce」。实测：

| 场景 | 输入规模 | 耗时 | 关键信息保留 |
|---|---|---|---|
| 典型单窗口 | ~200 条 | 3~5 秒 | 完整 |
| **真实量**：1000 条短消息 / 24 会话 | 18.8k 字 ≈ 10k tokens | **~25 秒** | **4/4 关键项全部识别** |
| **极端量**：800 条长消息 / 24 会话 | 88k 字 ≈ 80k tokens | **~55 秒** | **4/4 关键项全部识别** |

分块策略做过两轮修正：早期实现「一个会话一次模型调用」在 48 个会话时要 226 秒，改为**打包**后降到 53 秒；
早期实现超预算时**直接丢弃**多余摘要（实测 48 块丢 39 块），改为**多轮归并**（逐步浓缩而不是扔掉）。

**建议**：群消息量远大于私聊，**用白名单只加真正关心的群**。全量群采集时，单个窗口可能达到几千条，
虽然不会丢数据，但耗时会长到影响整点送达（预计算提前量默认只有 5 分钟）。

### 其它限制

1. **群消息默认不采集**，需要在界面里显式开启并配置白名单。
2. **归类边界存在主观性。** 实测中"帮忙内推""找发票"这类请求偶尔会被归到「值得知道」而非「需要我回复」。
   信息不会丢失（四个分类都会输出），但归类不一定完全符合预期。可在「提示词」页调整规则后用「小样整合」或 `selftest` 验证。
3. **图片、语音、视频只记录占位符**（`[图片]`、`[语音]`），不做 OCR 或转写。
4. **单档简报不跨档记忆**，每档独立整合。
5. **重要提醒按会话级生效**：把某人加入重要联系人后，他发来的**所有**消息都会被标为重要，包括闲聊。
6. **NapCat 一个实例只能登录一个账号**（官方设计如此）。本方案只需要 1 个实例。
7. **界面无自动刷新配置的能力**：多开界面编辑同一份配置时，后保存的会覆盖先保存的。
8. **`runs/` 留档不会自动去重**：反复点「生成简报」会产生多份 manual-* 留档，需要手动清理。
9. **同时只能有一个 qqdigest 实例监听 5700**。第二个实例会被明确拒绝（见常见问题）。

## 11. 风险提示

1. **使用 NapCat 属于第三方协议端，违反腾讯用户协议。** 账号可能被限制社交功能、冻结甚至封禁，后果自负。
2. **本方案由大号承担协议端风险**（这是"用大号采集"的必然代价）。一旦被限制社交功能，影响的是你所有聊天，不只是本功能。
3. 行为层面本方案是最温和的一档：不加人、不进群、每天 3 条私聊、不发敏感内容。主要残余风险是**客户端完整性检测**，与行为无关。
4. 实操禁忌：
   - 手机端**不要装任何 QQ 模块/插件**（LSPosed/Xposed 类），否则可能全端下线；
   - 官方 PC 客户端不要同时登录大号（会与 NapCat 实例互相踢下线）；
   - NapCat 的 WebUI 与 OneBot 接口**绝不能暴露公网**；
   - 一旦出现「社交功能被限制」，立即停跑，解锁后观察几天再决定是否继续。

## 12. 附：技术选型

**为什么零第三方依赖？** Python 3.11 标准库已提供本项目所需的全部能力：

| 需求 | 标准库方案 |
|---|---|
| 读 TOML 配置 | `tomllib` |
| 写回 TOML（保留注释） | 自实现 `qqdigest/toml_writer.py` |
| 本地存储 | `sqlite3` |
| 接收 NapCat 上报 | `http.server.ThreadingHTTPServer` |
| 调用本地模型 / OneBot API | `urllib.request` |
| 定时调度 | 自实现（`threading` + 时间计算） |
| 图形界面 | `tkinter` / `ttk` / `scrolledtext` |
| Windows 桌面通知 | 通过 PowerShell 5.1 调用 WinRT（不需 BurntToast） |
| 日志轮转 | `logging.handlers.RotatingFileHandler` |
| 子进程管理 | `subprocess` + `threading` |

好处：不需要 venv、不需要 pip 安装、不会因依赖版本冲突失效、换台机器复制即可运行。
传输层因此选用 OneBot 11 的 **HTTP 上报**而非 WebSocket（后者需要第三方库实现握手）。

**重要提醒为什么不用模型生成？** 见 [第 2 节](#关键设计-2重要提醒由代码生成不交给模型) 的踩坑记录。
